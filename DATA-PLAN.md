## Tested sources
### Aladhan Prayer Times API (api.aladhan.com)
**Used by**: getDayTimings, getRamadanCalendar, getTodayInfo server actions (fetch by district coordinates, method=1 Karachi 18°/18° = IFB Fajr standard, school=1 Hanafi Asr)
**Test command**: `curl -s 'https://api.aladhan.com/v1/timings/08-02-2027?latitude=23.8103&longitude=90.4125&method=1&school=1'` plus Jamalpur/Sylhet/Chattogram variants and `curl -s 'https://api.aladhan.com/v1/hijriCalendarByCity/1448/9?city=Dhaka&country=Bangladesh&method=1'`
**Sample output**: Dhaka 1 Ramadan 1448 (08-02-2027): Fajr 05:19, Maghrib 17:49 — exactly matching the independently published Wego IFB-standard table; Jamalpur Fajr 05:22/Maghrib 17:50, Sylhet 05:14/17:42, Chattogram 05:13/17:45 (real per-district differences); Hijri month 9 of 1448 has 29 days in the astronomical calendar
**Processing**: Sehri end = Fajr, Iftar = Maghrib; all 5 waqt (Fajr, Dhuhr, Asr Hanafi, Maghrib, Isha) + Sunrise shown; responses cached in a prayer_cache DB table per district+date so repeat opens are instant; UI always labels times as ইসলামিক ফাউন্ডেশনের পদ্ধতি (১৮°) অনুযায়ী হিসাব করা এবং চাঁদ দেখা সাপেক্ষে — never claimed as the not-yet-published official 1448 IFB chart

### BDAPIs district list (bdapis.com) — build-time only
**Used by**: embedded static district table in shared code (all 64 districts: Bengali name, English name, latitude/longitude) that powers the district picker and Aladhan coordinate lookups; NOT called at runtime
**Test command**: `curl -s 'https://bdapis.com/api/v1.2/districts'`
**Sample output**: HTTP 200, records like {district: 'Jamalpur', districtbn: 'জামালপুর', coordinates: '25.083, 89.785'}, current official spellings (Cumilla, Chattogram, Barishal, Jashore)
**Processing**: full 64-row list transcribed into a typed data file at build; coordinates feed Aladhan so every district gets its own times

### Islamic Foundation Fitra rates (1447, latest announced)
**Used by**: Fitra calculator reference rates + per-person × family-members calculation
**Checked with**: browser_search 'Islamic Foundation Bangladesh Fitra 2026 per person minimum maximum taka' — Prothom Alo / BSS / bdnews24 all report the National Sadaqatul Fitr Fixing Committee decision of 25 Feb 2026
**Sample output**: per person — আটা/গম (১.৬৫ কেজি) ৳110 (সর্বনিম্ন), যব ৳595, খেজুর ৳2,475, কিশমিশ ৳2,640, পনির ৳2,805 (সর্বোচ্চ)
**Processing**: shown explicitly as 'সর্বশেষ ঘোষিত হার (১৪৪৭ হিজরি)'; 1448 rates are not announced yet, so the calculator defaults to these and every rate field stays editable — nothing presented as the 2027 rate

## Static curated content (no runtime fetch)
- দোয়া ও হাদিস: সেহরির দোয়া, ইফতারের দোয়া, লাইলাতুল কদরের দোয়া, রোজার নিয়তসহ পরিচিত সহিহ দোয়া (আরবি + বাংলা অর্থ + সূত্র) এবং ৩০টি হাদিস (বুখারি/মুসলিম/তিরমিজি সূত্রসহ) বাংলা অর্থসহ — client bundle-এ curated static data, প্রতিদিন তারিখ অনুযায়ী একটি হাদিস/দোয়া ঘোরে
- যাকাত: নিসাব স্বর্ণ ৮৭.৪৮ গ্রাম (৭.৫ ভরি) / রৌপ্য ৬১২.৩৬ গ্রাম (৫২.৫ ভরি), হার ২.৫% — calculator takes নগদ টাকা, স্বর্ণ/রৌপ্যের পরিমাণ ও ব্যবহারকারীর দেওয়া বর্তমান বাজারদর (কোনো উদ্ভাবিত লাইভ দর দেখানো হবে না), ঋণ বাদ দিয়ে নিসাব যাচাই + যাকাতের পরিমাণ বের করে
- কোরআন খতম প্ল্যান: ৩০ দিনে ১ পারা/দিন (মোট ৬০৪ পৃষ্ঠা, দিনে ~২০ পৃষ্ঠা) static plan table + per-account check-off

## Long-term data behavior
- **Refresh policy**: prayer times fetched from Aladhan on first request per district+date, then served from prayer_cache; a 'রিফ্রেশ' tap can force-refetch today's times. No cron needed — Ramadan dates derive from the Hijri calendar API, not a stored schedule.
- **Growth**: users, sessions, roza_tracker (≤30 rows/user/year), khatam_progress (≤30/user/year), tasbih totals (1 row/user/dhikr), prayer_cache (bounded by districts × dates actually opened)
- **Ordering**: calendar ascending by Ramadan day; tracker and khatam keyed by (user, hijri_year, day)
- **Time semantics**: all times Asia/Dhaka; countdown computed client-side against the viewer's clock set to Dhaka time; last_active_at updated on login and app-open heartbeat for admin 'সক্রিয় ব্যবহারকারী' counts (আজ / গত ৭ দিন)
- **Auth/admin**: phone+password, password stored as salted SHA-256 hash, session token in DB; the FIRST registered account is flagged admin (builder note in summary: user must register first); admin stats action rejects non-admins server-side

## Edit 2026-11-26 — background alarm, day-detail calendar, twice-daily hadith notifications
- **Mechanism (client-side only, no new external source)**: the browser Notification API + in-page scheduling (`client/src/notify.ts`). While the app is open or backgrounded, timers fire (a) the Sehri alarm at Fajr − alarmMinutes with sound + banner + notification, and (b) the day's hadith at 08:00 and 19:00 Asia/Dhaka with the full Bengali text, topic and source in the notification body. Fired slots are remembered in localStorage; a slot missed within the last 4 hours (hadith) / 90 minutes (alarm) is delivered as a catch-up when the app returns. No server push channel exists in this runtime, so no cron was added.
- **Calendar day detail**: tapping any calendar row opens that day's full schedule (কততম রোজা, Gregorian + Hijri date, Sehri end/Fajr, Sunrise, Dhuhr, Hanafi Asr, Iftar/Maghrib, Isha, Qadr-night flag) from the same already-fetched Aladhan DayInfo rows — no new fetch.
- **Hadith topics**: `HADITH_TOPICS` in content.ts — one short topic label per existing curated hadith, derived from that hadith's own text; shown on Home, in the Dua tab's full-details list, and in notification titles.

## Edit 2026-11-26 (3) — login must work with the previously created account
- **Bug (reproduced in the sandbox)**: register/login stripped only spaces/dashes and compared the phone string exactly, so the same number typed as `+880171…` or with Bengali digits (০১৭…) failed login with "ফোন নম্বর বা পাসওয়ার্ড মিলছে না" even though the account existed; re-registering in another format silently created a duplicate account.
- **Fix**: a shared canonical form `01XXXXXXXXX` — Bengali digits converted to Latin, all non-digits stripped, `880…` → `0…`, bare 10-digit `1…` → `01…`. The server canonicalises on register (stores canonical, duplicate check matches any format) and on login looks the account up by canonical comparison, canonicalising legacy stored values on the fly so pre-fix accounts keep working untouched. The client normalises the typed number the same way before sending and the login form now says the earlier account's number works in any of these formats. No schema change; existing user rows are not rewritten.

## Edit 2026-11-26 (8) — automatic Fitra rate updates + full offline cache with auto-sync
- **Auto Fitra rates (server)**: rates moved from a client constant to the `app_settings` table (key `fitra_rates`, JSON; migration 0003). `getFitraRates` returns the stored rates, defaulting to the verified 1447 rates above until a newer announcement is saved. `saveFitraRates` (called only by the research task) replaces the stored rates only for a Hijri year >= the stored one. `refreshFitraRates` runs daily via cron job `ramadan-fitra-rate-daily-check` (~09:00 Asia/Dhaka): if the stored year is behind the upcoming Ramadan's year and no check ran in the last 20h, it spawns a background research task (ctx.agent.spawnTask, expectsAction=saveFitraRates) that must cross-check the announcement in at least two reliable published sources (Prothom Alo / BSS / bdnews24 / Dhaka Tribune / IFB) and saves nothing when the rate is not out or unverifiable — no guessed rates ever reach the app.
- **UI change**: the Fitra calculator no longer offers "নিজের হার বসান" (manual rate entry removed, per the user's ask); it shows the stored latest announced rate with its Hijri year, source body, announcement date and a link to the announcement report when one exists, and states plainly that the new rate arrives by itself and that offline the last received rate is what shows and is used.
- **Offline + auto-sync (whole app)**: `client/src/cache.ts` — every successful response for the essential queries (me/profile, today's + tomorrow's day timings, Ramadan calendar, my-state marks, Fitra rates) is written to localStorage (`rmjaan-cache:` keys) and used as the query's initialData on the next open. Offline, the app therefore opens fully on the last data it ever received (profile included, so no login wall); dua/hadith/Khatam plan were already static bundle content. TanStack Query's default refetch on mount/reconnect overwrites the cache in place whenever the connection returns — nothing for the user to tap. A slim note ("এখন ইন্টারনেট নেই — ফোনে সংরক্ষিত সর্বশেষ তথ্যই দেখানো হচ্ছে…") appears only when a fetch failed but cached data is on screen; the hard error card now shows only when there is no cached data at all. A Settings card ("অফলাইনেও সব চলবে") explains the behaviour in simple Bengali. Honest limit: changes made while offline (Roza/Khatam marks, settings) still need the connection to save — viewing and calculating work fully offline, saving syncs when back online.
